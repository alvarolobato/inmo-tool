# D-014: Comparable-rent estimator — selection rule, confidence tiers, and precedence vs. a profile's own assumption

*Decided: 2026-08-03*

**Context**: [D-010](D-010-rent-assumption-until-comparables.md) shipped a per-profile `€/m²/month` assumption as an explicit stand-in "until #31 ships real comparables" — issue #31 is that work. `RentConfidence` (`"high" | "low" | "assumption" | null`) was deliberately typed as a superset from the start so `"high"`/`"low"` could go from reserved-but-unreachable to real without a signature change (see the original `rent-estimate.ts` docstring). This decision makes three judgment calls the issue and the implementing brief both flagged as needing an explicit, documented answer.

**Decision**:

1. **Comparable selection**: same shape as `area-price.ts`'s sale-comparable query (median via `PERCENTILE_CONT`, a padded lat/lon bounding-box prefilter ahead of the exact Haversine expression, same `idx_property_lat_lon` index) with two differences tuned for rent specifically:
   - **Size-banded** (`SIZE_BAND_RATIO = 0.35`, comps within ±35% of the target's own `m2_built`): rent varies far more with size than sale price/m² does (a 40m² studio rents for much more per m² than a 150m² flat) — an unbanded median would systematically mis-scale for anything far from the local size mix. Sale comps aren't size-banded because condition and exact location dominate price/m² there more than size does. **Caveat (Opus review, PR #199)**: ±35% is a deliberately wide band, and its own reasoning is the argument for why a band alone isn't a complete fix — if nearby rental stock skews smaller than the target within that band (e.g. a 40m² target matched against mostly 26-30m² studios rather than 40-54m² flats), the median €/m²/month is biased toward the smaller end, which is itself biased high (small units rent for more per m² — the very effect the band exists to correct for) — overstating the target's estimated rent and therefore its yield. Not fixed in this PR; accepted as a v1 limitation given rental inventory's current sparsity (a tighter band would push most properties straight to `insufficient_data`). Revisit once rental volume is high enough to either narrow the band or weight comps by size-proximity within it.
   - **Looser radius** (`DEFAULT_RADIUS_KM = 1.5` vs. sale's `1`): rental inventory is far sparser today (one new connector vs. several existing sale connectors) — a tighter radius would push most properties straight to "insufficient data" regardless of how well-located the real comps are.
   - **Recency bound** (`MAX_COMP_AGE_DAYS = 30`, Opus review must-fix, PR #199): the rental connector never withdraws stale listings (`discovers_full_inventory = False`, so `_reconcile_missed_discoveries` never runs for it) and `normalize()` hardcodes `status="active"` — without a bound, a rental ad ingested once stays comp-eligible forever, even after the actual unit was re-rented months ago. The bound is on `listing.last_seen_at`, which `_update_last_seen_for_discovered` refreshes on every `discover()` run regardless of whether `fetch_detail()` succeeds — so it guarantees **presence** ("still listed within N days"), not **price freshness** ("price re-verified within N days"); see `rent-estimate.ts`'s module docstring for the precise distinction. `oldest_comp_age_days` surfaces the worst-case bound in the UI rather than implying false precision.

2. **Confidence tiers**: issue #31's own bands are the count gate, taken verbatim: below 3 comparables → no estimate (`insufficient_data`); 3–7 → `low`; 8+ → `high`. On top of that (per the implementing brief, not the issue itself), a dispersion gate demotes a sample whose comps disagree too much: `MAX_HIGH_CONFIDENCE_RELATIVE_IQR = 0.6` — the interquartile range of comps' €/m²/month, divided by their median. **Widened (Opus review, PR #199)** to apply at every tier, not just 8+: an 8+ sample failing it still demotes `high` → `low` (original behaviour); a 3-7 sample failing it now demotes past `low` entirely, to `insufficient_data` — there is no tier below `low` to demote a small, wildly-scattered sample INTO, so declaring it unusable is the only honest move (e.g. 3 comps at [5, 10, 30] €/m²/month: median 10, relative IQR 1.25, previously rendered a full `low`-confidence yield block off wildly disagreeing data). This can still only ever demote — never promote a small sample to `high`, never turn tight dispersion into usable data it wasn't otherwise.

3. **Precedence vs. a profile's own assumption**: the profile's `thesis_params.rent_assumption`, when set, remains the figure `yield.ts` actually computes from (`method: "profile_assumption"`, behaviourally unchanged from [D-010](D-010-rent-assumption-until-comparables.md)) — **never silently replaced by a measured comparable**, since a human may have encoded information the algorithm can't see (a specific building's condition, a negotiated rate, local knowledge). The market-comparable estimate is **always computed and attached** (`RentEstimateResult.market_comparable`) whenever the property has enough location data to query with, regardless of whether an assumption is set, and `disagreement_pct` is populated whenever both numbers exist. The UI (`YieldSection.tsx`) renders both, flags a disagreement ≥15% with a warning treatment, and — since must-fix #5 below — always names the sample size backing whichever figure is primary, not only when it's shown as a secondary line. "Show both", never "pick the one that looks more sophisticated". When no assumption is set at all, the market-comparable estimate becomes the PRIMARY figure.

   **Honesty about what this actually unblocks (Opus review, PR #199)**: the estimator itself is correct, tested machinery, but its data source is thin — `milanuncios_rental.py` inherits a `fetch_detail()` that hits a GeeTest wall after ~5 successes per run, city-wide (D-017), so `"high"` confidence is reachable in principle but not, realistically, in the sample volume this connector alone produces; `"low"` or `insufficient_data` is the normal outcome. This PR does not claim to have generally unblocked measured rental yield — see the follow-up issue (#211) tracking a viable rental data source, which is #31's actual remaining blocker.

**Alternatives rejected**:
- A single flat minimum-sample cutoff (mirroring `area-price.ts`'s `MIN_SAMPLE_SIZE = 5` single gate) — rejected because issue #31 explicitly asks for tiered confidence ("a median of 3 comparables and a median of 20 are not equally trustworthy"), not a pass/fail gate.
- Letting the measured comparable silently override or average with the assumption when both exist — rejected per the brief's explicit "do not silently replace the user's number" instruction; averaging two differently-sourced numbers (a judgment call and a measurement) would fabricate a third number neither source actually produced, the same anti-pattern [D-009](D-009-acquisition-cost-model.md) already rejected for carrying costs.

**Rationale**: The count-gate-plus-dispersion-demotion design keeps the issue's own explicit, reviewable numeric bands as the primary contract while still satisfying "confidence must mean something... tied to sample size and dispersion, not a vibe" — a `high` label now means both "enough comparables" and "comparables that roughly agree with each other," not just the former. The precedence rule keeps [D-010](D-010-rent-assumption-until-comparables.md)'s honesty guarantee (never fabricate, never silently override an explicit human input) while extending it to a population of profiles that never had a number to override in the first place.

**Status**: This decision **retires [D-010](D-010-rent-assumption-until-comparables.md)** — its "until #31 ships real comparables" condition is now met. D-010's file is marked retired rather than deleted (git archaeology); its line is removed from `DECISIONS.md`.
