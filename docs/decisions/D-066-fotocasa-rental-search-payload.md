# D-066: Rental comps come from Fotocasa's search-payload (coordinates included), not Milanuncios discover-only

*Decided: 2026-08-05*

**Context**: Issue #211. `dashboard/lib/analytics/rent-estimate.ts` is real, correct, size-banded comparable-rent machinery, but `MilanunciosRentalConnector` (issue #31, [D-015](D-015-rental-connector-site-choice.md)) can't feed it at volume: it inherits `fetch_detail()` from the sale connector, whose detail-page path hits a GeeTest wall after ~5 successes per run, city-wide (count-based, [D-017](D-017-milanuncios-rate-measurement.md)). #211 listed four candidates. Two were pursued offline for this decision; two are owner-gated (below).

The estimator's `queryMarketComparableRent` hard-requires **`property.lat` and `property.lon`** (padded lat/lon bounding box → exact Haversine radius), bands comps by `property.m2_built`, matches `property.property_type`, and reads the rent from `listing.current_price` (`operation='rent'`, `current_price > 0`). So every usable comp needs FOUR property fields — `lat`, `lon`, `m2_built`, `property_type` — plus a positive price. The orchestrator has **no geocoding fallback**: `property.lat/lon` is written straight from `canonical.lat/lon` (`etl/orchestrator.py`), so a connector that can't supply coordinates produces `lat/lon = NULL` rows that every comp query excludes.

**Candidate 3 (Milanuncios discover-only) — RULED OUT for the estimator.** Live-verified 2026-08-05 (the search-page endpoint is not walled, so this check was cheap and safe): `GET /alquiler-de-pisos-en-madrid-madrid/` returns HTTP 200 with `adListPagination.adList.ads[]` = 41 ads. Each ad IS rich — `price.cashPrice.value` (41/41), `category.slug` → property_type (41/41), and a `tags[]` array with `metros cuadrados`/`dormitorios`/`baños` → m2/rooms/baths (40/41). This **contradicts** the issue #143 comment's trimmed-fixture-based claim that the `ad` shape has "no price field" — the real payload does. **But it carries no per-listing geolocation at all (0/41; only `location.city`/`province`/`region`).** Deep-scanned every ad and the whole payload for any `lat`/`lon`/`geo`/`coord` key — none exist per-ad. Because the estimator hard-filters on `p.lat IS NOT NULL AND p.lon IS NOT NULL` and there's no geocoding step, a Milanuncios discover-only rental is invisible to the comp query. The one scarce field (lat/lon) is available only via the walled detail path; the cheap fields (price/m2/type) were never the bottleneck, so discover-only relieves nothing.

**Candidate 1 (sitemap/discover-payload source that avoids detail fetches) — FOUND: Fotocasa's rental search payload.** The servicer/bank portals that fit "sitemap-driven, avoid a detail fetch" (Solvia, Aliseda, Altamira, Cimenta2, Diglo) all publish **no coordinates** (verified in their own connectors' `normalize()`: `lat=None`; Solvia's own docstring: "no coordinates at all"), disqualifying them for the identical lat/lon reason. The one site that has BOTH a live, non-walled rental search endpoint AND per-listing coordinates in that endpoint's own JSON is **Fotocasa**. Live-verified 2026-08-05 with the connector's own honest `_USER_AGENT` (no CAPTCHA): `GET https://www.fotocasa.es/es/alquiler/viviendas/madrid-capital/todas-las-zonas/l` returns HTTP 200 with `initialSearch.result.realEstates[]` = 31 rental listings, **every one** carrying `coordinates.{latitude,longitude}` (31/31), `rawPrice` (31/31, `transactionTypeId == 3` = rent), `buildingType` (31/31, `"Flat"` → `map_property_type` → `"piso"`), and `features[]` with `surface` (31/31 m²), `rooms`, `bathrooms`, plus a full `address`. `robots.txt` (re-checked live) disallows only `/*clientId=*/alquiler/*`, `/*/alquiler/terrenos/*`, `/*/alquiler/edificios/*` — none match the `alquiler/viviendas/.../todas-las-zonas/l` dwellings path (no `clientId` param). This is the same `__initial_props__` blob `FotocasaConnector.discover()` already fetches for ids/prices — so the full per-listing record is available with **no detail fetch and no anti-bot wall**. Proven end-to-end offline against the real captured page: all 31 listings normalize with all four estimator fields + positive rent + `operation="rent"`.

**Decision**: Add `etl/connectors/fotocasa_rental.py` — `FotocasaRentalConnector(FotocasaConnector)`, a subclass (mirroring the milanuncios_rental precedent: a subclass in a new file, not an edit to `fotocasa.py`). It overrides `discover()` (fetches the rental search page, parses `realEstates[]`, stashes each full record on `self._search_records` keyed by external_id, returns ids), `fetch_detail()` (returns the stashed record with **no network I/O** and deliberately no `throttle()` call — the orchestrator does not itself rate-limit `fetch_detail`, relying on the connector's own `throttle()`, so a free operation is correctly unpaced), `normalize()` (maps the SEARCH `realEstates[]` shape — flat `features[]`, `rawPrice`, top-level `coordinates`/`address` — to canonical, `operation="rent"`), and `scope_key()` (geography-only, no rooms fold — this connector ignores room filters). Distinct `source="fotocasa_rental"`, own config/limiter/breaker rows. `rate_limit_per_minute = 3`, `discovers_full_inventory = False`, `min_refetch_interval_seconds = 0` — all declared explicitly. **Net footprint: exactly ONE Fotocasa HTTP request per scope per run** (discover's single page; every fetch_detail is served from that one payload). Born disabled (issue #100 generic mechanism).

**Milanuncios discover-only NOT implemented** — it would ingest coordinate-less rows the estimator can never use, adding schema noise for no estimator benefit. Milanuncios rentals stay on the existing `MilanunciosRentalConnector` (walled, born-disabled).

**Alternatives rejected**: (a) City-centroid geocoding for the Milanuncios/servicer payloads — collapses every city's listings onto one point, making the estimator's Haversine radius meaningless; dishonest precision. (b) Editing `rent-estimate.ts` to match comps by city instead of lat/lon — out of scope (#211/#199: the estimator is correct, untouched) and would abandon the size/location precision the whole module is built on. (c) Editing `fotocasa.py` to parameterize `comprar`/`alquiler` — a subclass in a new file is the smaller, precedent-following diff, and keeps the full-record capture (which the parent's price-only `discovered_prices` path doesn't do) self-contained.

**Owner-gated next steps** (need the owner's real residential connection and/or a DB run — do NOT run from a dev/cloud IP):
1. **Live DoD proof for Fotocasa rentals**: enable `fotocasa_rental` (set `connector_config.enabled = true`), run the orchestrator for a v1 market (e.g. Madrid) across a few daily cycles, then run `queryMarketComparableRent`-equivalent SQL against `property`/`listing` to confirm 8+ comps land within a 1.5 km + ±35% m²/`property_type` band for a real target. One search page already yields 31 estimator-ready Madrid rentals; band density accrues across runs.
2. **Volume lever (Fotocasa zone sweep)**: if page-1 city-wide density is too sparse for a band, extend `discover()` to the same per-neighbourhood zone sweep the sale connector runs (`_discover_zone_slugs` + zone loop, on the `/es/alquiler/...` path), stashing full records from every zone page. Deferred because it re-introduces a multi-request per-run footprint whose safe cadence needs a live measurement.
3. **Candidate 2 — Milanuncios `fetch_detail()` from the production residential IP**: the ~5/run wall (D-017) was only measured from a sandboxed dev IP. Re-test from the owner's home connection: run the existing `milanuncios_rental` connector once and read `connector_run_results` for its `fetched`/`errors` counts. A positive result is evidence, not proof of a non-count-based wall — treat as such.
4. **Candidate 4 — slower-cadence Milanuncios `fetch_detail()` measurement**: whether a 20–60 s/request cadence, tested only after a long enough gap for any prior lockout to clear, raises the ~5-request trip threshold. Costs a 60+-minute lockout per attempt on the owner's real connection — schedule deliberately, stop probing between attempts (polling may reset the decay timer).
