# D-085: Generate DECISIONS.md from per-decision frontmatter

*Decided: 2026-08-06*

**Context**: Issue #352. Every PR that recorded a decision appended a row to the
single hand-maintained `DECISIONS.md` index. Under parallel development this made
`DECISIONS.md` the merge bottleneck: any two in-flight PRs conflicted on it, so
landing N decision PRs cost ~N sequential rebases (observed repeatedly in one
session — ~7 PRs all appending). The decision-ID allocator (D-077 / #349) fixed
*ID uniqueness* but not the *file-level append conflict* — the rows still
collided on the same lines.

**Decision**: `DECISIONS.md` is a generated projection, never hand-edited. Each
`docs/decisions/D-NNN-<slug>.md` file carries in its YAML frontmatter the
binding-rule one-liner (`rule:`) and its group (`group:`); `scripts/build-decisions-index.py`
(logic in `scripts/decisions_index.py`) renders the preamble + grouped tables from
those files. Recording a decision = add one new `D-NNN-*.md` file (id via
`scripts/next-decision-id.py`) with `rule:`/`group:` frontmatter, then run the
generator. A file participates iff it has a non-empty `group` AND `rule`;
retiring a decision drops those fields (keeping the `## STATUS: retired` body
marker), which removes its row automatically. A drift guard
(`scripts/tests/test_decisions_index_fresh.py`, mirroring the `knowledge.ts`
guard) regenerates and asserts equality so a stale committed index fails CI.

**Ordering**: groups sort by the smallest `order` among their members; rows
within a group sort by (`order`, id). `order` is optional — the #352 migration
stamped an explicit `order` on every pre-existing record to reproduce the
hand-curated sequence byte-for-byte, but a NEW record omits it and simply
appends to the end of its group by id, so no cross-PR coordination is needed.

**Alternatives rejected**:
- *Keep hand-editing, rely on the ID allocator alone* — D-077 stops duplicate
  ids but two PRs still append rows to the same region of `DECISIONS.md` and
  conflict. The append point is the bottleneck, not the id.
- *Sort rows purely by id* — would not reproduce the hand-curated within-group
  order (e.g. connectors are grouped by theme, not id), making the migration
  lossy. An explicit-but-optional `order` reproduces the current file exactly
  while letting new records append trivially.
- *Drop the index entirely* — the flat one-line-per-rule view is the whole
  point (agents skim it in-context); generating it keeps that affordance with
  no manual upkeep.

**Rationale**: Removes the last file-level serialization point for parallel AI
work. Combined with D-077 (ID allocation), decision-recording is now fully
parallel-safe: two PRs adding different `D-NNN` files never touch the same
lines, and any residual `DECISIONS.md` conflict is resolved mechanically by
re-running the generator rather than by hand-merging prose.
