# D-147: Unfiltered scope sentinels — everywhere / all, never an absent field

*Decided: 2026-08-21*

**Context**: Issue #659, the enabler for #658's "novedades" profile — the owner wants a profile that takes small portals wholesale and filters afterwards in the list. `ScopeSchema` (`dashboard/lib/profiles-schema.ts`) required `geography` (a radius) and `property_types` (≥1 element), so there was no way to create it. The obvious shortcut — make both fields `.optional()` — was considered and rejected: Fable's judgement on #658 traced the real landmines it would hit — `scope-query.ts`'s `ANY($n::text[])` clause would bind `undefined`/`NULL` for an absent `property_types`, which Postgres evaluates to **zero rows**, the exact silent-failure D-013 was written to prevent; `geography.type`/`.center` are dereferenced unguarded in `scope-query.ts`, `scopesEqual`, `profile-diagnostics.ts`, and `search-url/index.ts`; and the ETL's `_active_profile_scopes` warn-and-skips anything non-radius, which would spam a warning every sweep for a profile that was never broken, only unfiltered on purpose.

**Decision**: "Everything" is a value someone must explicitly write, exactly like every other scope field. `geography` becomes a Zod discriminated union — `{type:"radius", center, radius_km}` (unchanged) or `{type:"everywhere"}` (new, `.strict()` so it can't silently carry stale radius fields). `property_types` becomes `z.union([z.literal("all"), z.array(z.enum(PROPERTY_TYPES)).min(1)])`. An object that omits either field still fails `ScopeSchema.parse` exactly as before — D-013's guarantee ("a missing scope fails loudly, not silently") is unchanged; what's new is a second way to be *present and valid* short of naming a radius or a type list.

Every unconditional consumer got a real branch instead of an accidental fallthrough:
- `scope-query.ts`'s `buildScopeFunnelStages`: `everywhere` drops the haversine/lat-lon clause entirely (no params), but the unconditional `status='active' AND operation='sale'` EXISTS (D-016) is unconditional in the literal sense — it survives regardless of which geography branch ran. `property_types: "all"` omits the `ANY(...)` condition outright rather than ever binding a NULL/undefined array. A geography type outside the union still throws (exhaustiveness guard) rather than silently matching every property.
- `profile-diagnostics.ts`: an `everywhere` scope's zero-candidate diagnosis has no center to compute "nearest property" or "area coverage" against — `radiusKm`/`nearest`/`areaCoverage` are `null` in that case (type widened accordingly in `profile-diagnostics-types.ts`), and the UI (`ZeroCandidatesDiagnostic.tsx`) renders a plain "no active sale listing in the whole database yet" instead of a fabricated radius/coverage claim.
- `search-url/index.ts`'s `canonicalScopeFromProfile` returns `null` for `everywhere` (no center a portal URL builder's grammar could work from) — `buildSearchUrl`/`buildSearchUrls` propagate that as "no derived tasks", not a crash. `"all"` property_types expands to the full `PROPERTY_TYPES` list before reaching a builder, so a radius+all scope still fans out one task per type exactly like an explicit full list does today. `resolve.ts`'s `resolveSearchTasks` still resolves an owner-pinned override (D-101) for an `everywhere` profile even on a portal that HAS a builder — same posture the ETL's `_override_scopes_for_connector` already takes for a malformed geography: a pin is a valid recall source on its own, independent of geography.
- `etl/orchestrator.py`'s `_active_profile_scopes`: an `everywhere` geography is recognised and skipped **quietly** (debug log, "handled by everywhere-crawl semantics" — not yet built) rather than the existing malformed-geography warning. A genuinely malformed/missing geography still warns exactly as before.
- `scopesEqual`: a radius↔everywhere transition, or an explicit-list↔"all" transition, IS a scope change — D-040's quick refresh (re-materialize + full sweep) fires on it. `"all"` is compared as a first-class sentinel, never unwrapped and never treated as equal to an explicit list that happens to name every type (they're different stated scopes: one tracks future new types automatically).

Two consequences are deliberate, not bugs: dropping the radius clause also drops its implicit `lat/lon IS NOT NULL` requirement, so an `everywhere` profile is the first thing that can ever match an un-geocoded property (695 in production at design time) — a real recall gain, verified in `materialize.integration.test.ts`. And `ProfileForm.tsx`'s two sentinel toggles are paired with a `POST /api/profiles/scope-preview` draft-scope COUNT, shown as a warning line whenever either sentinel is active, so the owner sees the actual match count before saving — visibility, not a block, against accidentally creating a full-pool (11.6k property, ~$180-320 LLM backlog) profile instead of the intended small-portal one. The connector-selection guard that makes a small profile *safe by construction* is #660/#663, sequenced after this issue; this PR is the enabler only.

**Alternatives rejected**: `.optional()` fields (see Context — silent zero-match binds, unguarded dereferences, warning spam). A single `geography: null` sentinel instead of a discriminated union — rejected because it still requires every consumer to special-case `null` vs. the existing object shape, with none of the type-safety a discriminated union's exhaustiveness checking gives for free.

**Rationale**: D-013's actual guarantee — an absent scope fails loudly — is orthogonal to whether "no filter" should be expressible at all. Extending the schema with real sentinel values preserves the guarantee (nothing about presence/absence changed) while adding the one new capability the owner asked for, and forces every unconditional consumer to make a deliberate choice about what "everywhere"/"all" means for it rather than inheriting undefined behavior.
